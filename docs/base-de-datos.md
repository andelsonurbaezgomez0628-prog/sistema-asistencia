# Diseno de la base de datos

Motor: **PostgreSQL en Neon**. La estructura academica vive en `sql/schema.sql`, los registros
ficticios en `sql/datos_demo.sql` y las sesiones en `sql/sesiones.sql`. Node.js accede mediante
`pg`; la URI se configura en `.env` y no se incluye en el repositorio.

## 1. Instalacion

```powershell
npm run db:setup
```

El instalador conserva el esquema completo y sus datos. Una base vacia recibe las seis tablas
academicas, el escenario demo y una tabla separada para sesiones. Si detecta tablas parciales,
se detiene. Si la base ya existia con `estudiantes.cedula`, aplica
`sql/migracion_numero_lista.sql` para conservar estudiantes, asistencias y alertas. La
reinstalacion destructiva exige respaldo y confirmacion:

```powershell
npm run db:setup -- --forzar --confirmar
```

## 2. Relaciones

```text
usuarios 1:N secciones N:1 cursos
secciones 1:N estudiantes
estudiantes 1:N asistencia (UNIQUE estudiante_id + fecha)
estudiantes 1:N alertas
sesiones: persistencia independiente de login
```

Un docente tiene secciones asignadas. Cada estudiante pertenece a una seccion. Las claves
foraneas impiden referencias huerfanas; las rutas ademas verifican que cada objeto pertenezca
a la cuenta autenticada.

## 3. Tablas academicas

| Tabla | Campos relevantes | Regla |
|---|---|---|
| `usuarios` | identidad, `password_hash`, `rol`, `activo BOOLEAN` | usuario/cedula unicos; roles admin/docente |
| `cursos` | nombre y descripcion | nombre unico |
| `secciones` | curso, docente, ano escolar | nombre unico dentro del curso |
| `estudiantes` | numero de lista, datos, seccion y activo | numero unico dentro de la seccion (1-40); desactivar preserva historial |
| `asistencia` | estudiante, fecha, estado, autor | UNIQUE por estudiante/fecha; enum controlado con CHECK |
| `alertas` | nivel, faltas, racha, explicacion, estado | conserva evidencia del calculo |
| `sesiones` | id opaco, expiracion, JSON serializado | expira y se elimina al cerrar sesion |

Las claves primarias usan `GENERATED BY DEFAULT AS IDENTITY`. `activo` es `BOOLEAN`; estados y
roles son `VARCHAR` limitados por `CHECK`. Las claves foraneas y restricciones estan en el
esquema SQL para que PostgreSQL tambien proteja la integridad.

## 4. Consultas PostgreSQL usadas por la aplicacion

**Ventana de ausencias y tardanzas:**

```sql
SELECT COUNT(*) FILTER (WHERE estado = 'ausente') AS faltas,
       COUNT(*) FILTER (WHERE estado = 'tardanza') AS tardanzas
FROM asistencia
WHERE estudiante_id = $1 AND fecha BETWEEN $2::date - 29 AND $3::date
```

**Upsert de asistencia:**

```sql
INSERT INTO asistencia (estudiante_id, fecha, estado, observacion, creado_por)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (estudiante_id, fecha)
DO UPDATE SET estado = EXCLUDED.estado, observacion = EXCLUDED.observacion
```

Todas las entradas usan placeholders `$1`, `$2`, etc. Los nombres de tabla dinamicos solo se
usan desde listas internas constantes. Para reportes se usan `COUNT(...) FILTER (WHERE ...)`,
`CURRENT_DATE` y aritmetica de DATE de PostgreSQL.

## 5. Reglas que no deben romperse

- `justificado` no cuenta como falta de riesgo.
- `tardanza` cuenta como asistencia en los porcentajes.
- Tres ausencias no justificadas en 30 dias: medio; cinco o racha de tres dias: alto.
- Cuatro tardanzas suman un punto.
- Estudiantes/docentes con historial se desactivan, no se borran.
- Al guardar una asistencia existente se actualiza la fila, no se duplica.
- La fecha de referencia procede de `CURRENT_DATE` de PostgreSQL.

El demo debe conservar 3 cursos, 4 secciones, 20 estudiantes, 50 marcas y 4 alertas pendientes.
Al insertar IDs fijos, el seed reajusta las secuencias con `setval` para no chocar al crear nuevos
registros.
